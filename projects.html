Projects we will work on

Five projects that give you the thing reading cannot: a system that went wrong and a story you can tell about it. Each project ends with a story in five parts.

Status of this page. No project here was run as a whole. Every command is copied from a module or from the capstone page, and every outcome is described, not predicted. Where a step uses something no module shows, it carries the tag unverified and the words "not run in the labs". Time estimates are guesses, not measurements. Numbers such as 5,000 partitions are targets to attempt. Your laptop may not reach them.

Rules for all projects

  • Write down every number. Copy the command and its output into your log at the moment you run it. Memory changes the story.
  • Keep a log file. One file per project, with a line for each action, in the format below. Write your guess before the run, not after.
  • Run the three health checks before and after. They come from module 09, step 1. Output means something is wrong. No output means healthy.
  • Never claim a result you did not measure. If you did not run it, say "I did not run it". This is not a weakness. It is the sentence that makes the rest believable.
  • Run one project at a time. If the cluster is left broken, docker compose down then docker compose up -d. This removes container data.

Project B

Scale lab: how many partitions can the lab hold?

Difficulty 2 of 31 week10 to 15 hours (estimate)
0 of 8

Purpose

Module 09 says too many partitions is a failure, but gives no feel for where "too many" starts. In this project you add partitions in steps and watch what each step costs: creation time, memory, restart time, failover time, and the size of the cluster metadata log. You will not find a universal limit. You will learn which number moves first and how to measure it.

Spec

  • Main three-broker cluster only. The monitoring profile is optional, and helps for JMX.
  • Create topics with replication factor 3 in steps of total partitions: for example 500, 1,000, 2,000 and 5,000. These are targets to attempt.
  • After each step: run the three health checks, record every measurement in the table below, then go on.
  • Run the restart test and the failover test at the smallest step and again at the largest step you reach.
  • Keep the Docker memory stop rule, below.

The loop

The topic command is the one from modules 01 and 03. The loop around it is yours to adapt.

# one step: add 5 topics of 100 partitions each (500 partitions in this step)
for i in $(seq 1 5); do
  k kafka-topics.sh --bootstrap-server $B --create --topic scale-a-$i \
    --partitions 100 --replication-factor 3
done
# next steps: change the topic names (scale-b-..., scale-c-...) and the counts.
# every partition has 3 copies, so 500 partitions mean 1,500 replicas in the cluster.

Stop rule. The 1,000 to 5,000 partitions are a target to attempt. Your laptop may not reach it. Watch the memory Docker Desktop shows. If Docker runs out of memory, a broker container exits, or a command stops answering, stop and write down the last step that worked. Do not push on. To clean up, use docker compose down and docker compose up -d in the main folder. Drills say this removes the container data.

Real hardware differs from a laptop in memory, disk speed and network. Never say "Kafka handles N partitions" from this project. Say "my three-container lab did or did not hold N".

Incident replay: three incidents, three reports

Difficulty 2 of 32 weeks12 to 20 hours (estimate)

Purpose

Staff-level interviews ask how you handle a bad day. In this project you pick three incidents from the table, break the lab on purpose, observe, repair, and then write a post-incident report for each. The report is the point. Writing a timeline from your own log shows you what you missed.

Spec

  • Pick three incidents from the table. Pick at least one that touches replication or the controller, and one from the client side.
  • Use the matching drill on drills.html for the commands. Do not skip its questions.
  • For each incident: reproduce, observe, repair, then write the report. Use the template below.
  • As a reading step, open case-studies.html and compare each incident with a published case.
  • Run the three health checks before and after each incident.

Project D

Lag monitor for Kafka 4.3

Difficulty 3 of 32 weeks15 to 25 hours (estimate)
0 of 8

Purpose

Module 12 found that the lab exporter could not read consumer groups from Kafka 4.3, so the lab has no lag metric and no lag alert. Real teams meet this: a tool stops working after an upgrade. You will build a small replacement in a language you know. It reads lag from the command-line tool, turns it into metrics, and raises one useful alert.

This card gives the spec and the tests only. You write the tool.

Spec

  • Run kafka-consumer-groups.sh --describe --all-groups (module 03) every 30 seconds. Run it through docker exec on a broker, as the modules do.
  • Parse the columns GROUP, TOPIC, PARTITION, CURRENT-OFFSET, LOG-END-OFFSET and LAG for every group.
  • Compute lag in records for each partition. Check it against the LAG column.
  • Estimate lag in time: lag in records divided by the end-offset rate (records per second, measured over a window you choose). Decide what to publish when the rate is zero.
  • Publish the numbers where Prometheus can read them: a text file or a small HTTP endpoint. Name the metrics yourself and label them with group, topic and partition.
  • Write one alert rule: a partition's committed offset has not moved for a time you choose, while its end offset has moved.
  • Survive broker restarts. If one broker is down, try another, as module 05 does with kafka-2.
  • Say what happens when a partition has no committed offset yet. unverified not run in the labs: the output for a group with no commit on a partition. Run it and record what you see.

What the labs do and do not show. Module 12 shows the Prometheus rules and metric queries on port 9095, and the rule file format in monitoring/alerts.yml (alert, expression, wait time, labels, annotations). The labs do not show a text-file or endpoint source added to Prometheus. unverified not run in the labs: adding a scrape target to monitoring/prometheus.yml, reloading Prometheus, and letting the Prometheus container reach a program on your laptop. Finding a working way, and writing it down, is part of the project. Note that the lab mounts both files read-only inside the container; you edit your copy on disk.

  • Lag in time estimate against the real measure in test D6.
  • Time for the tool to recover after the cluster restart in D5.

Project E

Multi-cluster failover rehearsal with MirrorMaker 2

Difficulty 3 of 31 to 2 weeks12 to 20 hours (estimate)
0 of 8

Purpose

Module 10 says a copy is not the original. Offsets differ, transactions are not preserved the way you hope, and failback is harder than failover. In this project you rehearse a real failover with a runbook and a stopwatch, then count what it cost. You also reproduce one problem module 10 reports and test its proposed fix.

Spec

  • Copy topics from main to kafka-dr with MirrorMaker 2, using the module 10 part B steps. Start the second cluster with docker compose up -d kafka-dr.
  • Translate group offsets (module 10 shows this with sync.group.offsets.enabled).
  • Stop the main cluster. Start consumers on the standby from the translated offsets. Switch producers to the standby.
  • Measure copy delay and repeated records.
  • Reproduce the aborted-records problem from module 10, then test a read_committed copying consumer.
  • Module 10 marks this fix unverified unverified: it did not rerun the lab. Your job is to find the right property name, set it, and record what you find. Do not trust a name from memory. Do not trust the module. Write down where you found it and what happened.
  • Write the runbook before the rehearsal, and time the rehearsal against a target of 15 minutes. The target is a number to attempt. No module measured a failover time.

Runbook template

FAILOVER RUNBOOK: main -> kafka-dr
Decision rule   (what exact condition makes us fail over? e.g. main unreachable for ___ minutes)
Who decides     (a named role and a named backup; who tells the others)
Stopwatch       start ___ : ___ ; target 15 minutes total; stop ___ : ___
1. Stop the copy        (command; confirm the copy process has ended)
2. Record last offsets  (source end offsets if readable; copy end offsets; translated group offsets)
3. Switch producers     (new address; which topic name on the standby; who changes the settings)
4. Start consumers      (group name; the offsets they start from; how you check them)
5. Verify               (health checks on the standby; sample records; count of repeats)
6. Rebuild the old site (what to start; what is stale; how to resync; who confirms)
Known losses    (records not copied; repeated records; aborted records visible?)

Failback (return to the main cluster) is harder than failover. Module 10 explains why. Write down what you would do, and mark each step you did not run. unverified not run in the labs: any failback.

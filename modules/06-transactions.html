Transactions and exactly-once

A transaction makes several writes succeed or fail together. With it, an application that reads from Kafka and writes to Kafka can give each input exactly one effect, even through crashes. The guarantee is real, and it stops at the edge of Kafka.

What it is and why it exists

Module 02 showed that idempotence stops duplicates from one producer's retries to one partition. Many applications need more. A typical one reads a record from an input topic, computes something, writes results to one or more output topics, and commits its input offset. That is three or more writes. If the application crashes between them, some are done and some are not, and after a restart the input is processed again.

A transaction groups those writes. Either all of them take effect or none does. The group can include records for several partitions and topics, and also the consumer group's offset commit, because an offset commit is itself a record in a Kafka topic.

Readers take part too. A consumer with isolation.level=read_committed does not receive records from a transaction until it has committed, and never receives records from one that was aborted.

Exactly-once in Kafka means this: for a read-process-write application, each input record affects the output topics and the committed offset exactly one time. It does not mean that your code runs once, and it does not cover anything outside Kafka.

The one-sentence version. A transaction writes records and offsets as one all-or-nothing unit, marks the outcome in the log, and readers that ask for committed data skip everything else.

offset 1

Mental model

Records of a transaction are written to the log at once, like any other records. They are not held back somewhere. What comes later is a small extra record, a marker, that says "the transaction of producer X is committed" or "is aborted". Readers decide what to show by looking at the markers.

  • A read_uncommitted reader, the default, shows every data record as soon as it is replicated. It ignores the outcome.
  • A read_committed reader stops at the first record of the oldest transaction that is still open. That position is the last stable offset. When the marker arrives, it moves on, and drops the records if the marker says abort.

Use the demo at the top. Write three records and commit: both readers show three. Write two more and press "Producer crashes": the first reader shows five, the second still shows three and waits. That waiting is the price of the guarantee, and it is the first thing that goes wrong in production.

offset 2

How it works internally

The parts

  • transactional.id: a name you give the producer. It must be stable across restarts of the same logical instance. It is how Kafka recognises "the same producer, restarted".
  • Transaction coordinator: a broker that tracks the state of each transaction. It is the leader of one partition of the internal topic __transaction_state; the hash of the transactional id picks which of the 50 partitions.
  • Producer id and epoch: the numbers from module 02. With a transactional id, the same producer id survives restarts and the epoch goes up.
  • Markers: control records written to each partition that took part. A marker uses one offset.

One transaction, step by step

  1. initTransactions(). The producer finds its coordinator and registers its transactional id. The coordinator raises the epoch. Any older process with the same id is now fenced: its next request is refused. The coordinator also finishes any transaction the old process left open.
  2. beginTransaction(). This only changes the producer's local state.
  3. send(). Records go to the partition leaders as usual, flagged as transactional. The coordinator learns which partitions take part.
  4. sendOffsetsToTransaction(). The consumer's offsets are added to the transaction. They are written to __consumer_offsets but do not count until the commit.
  5. commitTransaction(). The coordinator writes "prepare commit" to its own log. From this moment the outcome is decided, even if the coordinator crashes.
  6. The coordinator sends a commit marker to every partition that took part, including the offsets partition.
  7. The coordinator writes "complete commit". The transaction is finished.

Steps 5 to 7 are a two-phase commit. Step 5 is the decision. Steps 6 and 7 can be repeated safely after a failure, by the same coordinator or by its replacement.

How a read_committed consumer filters

The broker returns records only up to the last stable offset. For aborted transactions, each segment has a small file, the transaction index, that lists the offset ranges of aborted transactions. The broker sends that list with the data, and the consumer drops those records. unverified: the index file was not inspected in the lab

The transaction timeout

If a producer starts a transaction and then disappears, its records would block committed readers for ever. So every transaction has a timeout, transaction.timeout.ms, 1 minute by default. When it passes, the coordinator aborts the transaction and raises the epoch, so the old producer cannot continue. The broker refuses a timeout above transaction.max.timeout.ms, 15 minutes.

The epoch rises with every transaction

In the lab, the producer epoch was 3 after three transactions and 5 after two more. In Kafka 4 the coordinator raises the epoch at the end of each transaction, which closes a gap where a late message from one transaction could be mistaken for part of the next. unverified: the lab showed the numbers; the reason is from memory

What it costs

Each transaction adds a few requests to the coordinator and one marker for each partition. For large transactions the cost is small. For one record in each transaction it is large. The usual practice is to commit a batch every 100 milliseconds to a few seconds. A longer interval gives more throughput and makes committed readers wait longer.

Failure scenarios

A producer dies with a transaction open

What breaks
Committed readers of every partition in that transaction stop at its first record. Later records from other producers wait behind it.
You observe
Lag grows for read_committed consumers while read_uncommitted consumers keep up. kafka-transactions.sh describe shows the state Ongoing. In the lab: 68 records visible to one reader, 30 to the other.
What happens next
After transaction.timeout.ms the coordinator aborts it. In the lab, with a 40-second timeout, the state changed to CompleteAbort about 45 seconds after the transaction began: the timeout plus the coordinator's 10-second check. If the producer restarts sooner with the same transactional id, initTransactions() aborts it at once.
Fix
Keep the timeout as low as your processing allows. Restart crashed instances quickly with the same id.

The producer is fenced

You observe
A "producer fenced" or "invalid producer epoch" error on send or commit.
Cause
Another process started with the same transactional id, or the coordinator aborted this producer's transaction after a timeout.
Fix
This error is final for that producer object. Close it and exit or create a new one. If two live instances share an id by mistake, they will fence each other in turn: give each instance its own id.

Processing takes longer than the timeout

What breaks
The coordinator aborts the transaction while your code is still working. The commit fails, the batch is processed again, and it times out again.
Fix
Make batches smaller with max.poll.records, or raise transaction.timeout.ms. Both limits apply: the batch must also finish within max.poll.interval.ms.

A consumer shows aborted data

What breaks
A downstream system receives records that were rolled back.
Cause
The consumer uses the default read_uncommitted. Transactions on the producer side protect nobody unless readers ask for committed data.
Fix
Set isolation.level=read_committed. Check every consumer of the topic, including connectors and tools.

Duplicates in an external system

What breaks
The application sends an email or writes a database row during processing, the transaction aborts, and the retry does it again.
Cause
The transaction covers only Kafka.
Fix
Move the outside effect behind a topic: write a "send email" record in the transaction, and let a separate consumer send it with an id that the receiver can use to ignore repeats.

The transaction coordinator is not available

What breaks
Producers cannot start or commit transactions. Plain producers are not affected.
Cause
The partition of __transaction_state for that id has no leader or is below its in-sync minimum.
Fix
Treat it like any partition in that state (module 04). This is why the internal topic needs 3 copies.

Record counts and offsets do not match

You observe
A topic's end offset is higher than the number of records consumers received. In the lab: 30 records, end offset 33.
Cause
Each marker uses an offset. Aborted records also use offsets and are not delivered.
Fix
Nothing is wrong. Do not use offset arithmetic to count records on transactional topics.

Common mistakes and misconceptions

People thinkWhat is true
Exactly-once means my code runs once for each record.Your code can run several times. What happens once is the committed result in Kafka.
Turning on transactions in the producer is enough.Consumers must set read_committed, or they receive aborted records.
Uncommitted records are kept in a buffer.They are in the partition log at once. Markers and the reader's isolation level decide what is shown.
A Kafka transaction can include my database.It covers only one Kafka cluster.
Any unique string works as a transactional id.It must be the same after a restart. A random id each time gives no fencing, and old transactions wait for the timeout.
Transactions make Kafka slow.The cost is per transaction, not per record. With batches of hundreds of records it is small.
Idempotence and transactions are the same thing.Idempotence removes duplicates from retries to one partition. Transactions make writes to many partitions atomic and survive restarts.
offset 7

Staff-level questions

When are transactions the right tool, and when are they not?

Right: a stream processing step that reads from Kafka and writes to Kafka, where a duplicate in the output is a real problem, such as money totals or counts that later steps trust.

Not needed: when consumers can ignore repeats cheaply by an id, or when occasional duplicates do no harm, such as metrics. Not sufficient: when the important effect is outside Kafka. There a transaction gives a false sense of safety.

How do you choose transactional ids for an application with ten instances?

Each instance needs an id that no other live instance uses and that the same instance gets again after a restart. A stable instance number from the deployment system works: application name plus that number.

With a random id for each start, a crashed instance's open transaction is not aborted by its replacement, and blocks committed readers until the timeout. With a shared id, instances fence each other. Kafka Streams manages ids for you.

A team reports that their read_committed consumer is stuck but the topic is growing. What do you check?

An open transaction on that partition. Compare the consumer's position with the partition's last stable offset. List transactions and look for one in state Ongoing for longer than expected; the describe output shows its producer, its start time and its timeout.

If the producer is gone, the coordinator aborts it at the timeout. If the timeout is very long, kafka-transactions.sh has an abort command for an operator to end it. Then fix the cause: a timeout set too high, or instances that restart with new ids.

How does the commit interval trade throughput against latency?

Committed readers see nothing until the commit. So the commit interval is added to the end-to-end delay. A commit every 100 milliseconds keeps delay low and spends more on coordinator requests and markers. A commit every 5 seconds is cheap and makes every reader up to 5 seconds late, and a failure repeats up to 5 seconds of work.

Choose from the delay the readers accept, then check that the transaction rate is acceptable for the coordinator.

Why must offsets be committed through the producer in this pattern?

The output records and the input offset must share one fate. If the consumer commits the offset separately, a crash between the two steps gives either repeated output or skipped input. sendOffsetsToTransaction() puts the offset commit under the same marker as the output.

The call also passes the consumer's group metadata, so that a consumer that was removed from the group in a rebalance cannot commit offsets for partitions it no longer owns.

What does exactly-once cost the cluster?

Extra load on the coordinators and on __transaction_state. One marker write for each partition in each transaction. Memory in each partition leader for producer state. And an operational risk: any open transaction delays every committed reader of that partition, so one misbehaving client can affect others.

Self-test

1. What can one Kafka transaction contain?

Records for any topics and partitions in one cluster, and consumer group offset commits.

2. What is a marker?

A control record that the coordinator writes to each partition of a transaction to say commit or abort. It uses one offset.

3. What is the default isolation level of a consumer?

read_uncommitted.

4. What is the last stable offset?

The offset of the first record of the oldest open transaction in the partition. Committed readers read only below it.

5. What does initTransactions() do to an older process with the same transactional id?

It raises the epoch, so the older process is fenced, and it finishes any transaction that process left open.

6. A producer crashes with a transaction open. What ends the transaction?

The coordinator aborts it after transaction.timeout.ms, or a restarted producer with the same id aborts it in initTransactions().

7. Which step of a commit decides the outcome?

The coordinator writing "prepare commit" to its own log. Everything after it can be repeated.

8. A topic has 30 records and its end offset is 33. Why?

Three transactions were committed, and each commit marker uses one offset.

9. Name one effect that a Kafka transaction cannot make exactly-once.

Anything outside Kafka: a database write, an email, a call to another service.

10. Which tool shows open transactions?

kafka-transactions.sh, with list and describe.

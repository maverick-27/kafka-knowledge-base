The log

Everything in Kafka is built on one data structure: a file that only grows at the end. Learn this module well and the other nine become much easier.

A partition. Each new record goes to the end and gets the next number, its offset. Nothing is edited in place. Records written so far: 0

offset 0

What it is and why it exists

Kafka stores records. A record is one message: a key, a value, a timestamp, and optional headers. Records with the same purpose go into a topic, which is a named stream such as orders.

A topic is split into partitions. Each partition is a log: an ordered list of records that only grows at the end. Kafka gives every record in a partition a number, the offset. The first record is offset 0, the next is offset 1, and so on. An offset never changes and is never reused.

This design exists because it is simple and fast. Writing to the end of a file is the cheapest thing a disk can do. Reading is also cheap: a reader only needs to remember one number, the next offset it wants. Many readers can read the same data at different speeds, and a reader can go back and read old data again. The data stays until a retention rule removes it. Reading a record does not delete it.

The one-sentence version. A topic is a set of append-only files; producers add to the end, consumers remember how far they have read, and the broker deletes old data by a time or size rule.

offset 1

Mental model

Think of a topic as several notebooks, one for each partition. You can only write on the next empty line. Each line has a line number. Readers keep a bookmark. When a notebook is old enough, Kafka tears out whole pages from the front.

Three facts follow from this picture.

  • Order exists only inside one partition. There is no order between two partitions.
  • The key decides the partition. Records with the same key go to the same partition, so they stay in order.
  • Offsets belong to a partition. Offset 5 in partition 0 and offset 5 in partition 2 are different records.

Try it: the key picks the partition

Send records with different keys. The same key always lands in the same lane. This demo uses murmur2, the hash function of the Java client. I checked it against three values from Kafka's own tests.

A record with no key has no hash. The producer then fills one batch for one partition and moves to another partition for the next batch. Module 02 covers this "sticky" behaviour.

What a partition looks like on disk

A broker is one Kafka server. On a broker, each partition is a directory. The directory name is the topic name, a dash, and the partition number. Inside, the log is cut into files called segments. Only the newest segment, the active segment, receives writes.

offset 2

How it works internally

A write

  1. The producer groups records into a record batch and sends the batch to the broker that leads the partition.
  2. The broker checks the batch (size, checksum) and gives it the next offsets.
  3. The broker appends the batch to the end of the active segment. The bytes go to the operating system's memory first (the page cache). The operating system writes them to disk later.
  4. Each time about 4 KiB of data has been added (index.interval.bytes), the broker adds one entry to the .index file and one to the .timeindex file.
  5. When the active segment is full or old enough, the broker closes it and starts a new one. This is a roll.

Kafka does not force each write to disk by default. The defaults for flush.messages and flush.ms are the largest possible number, which means "let the operating system decide". Kafka gets its safety from copies on other brokers, which is module 04.

Why it is fast

  • Sequential writes. The disk head, or the solid-state drive controller, never jumps around.
  • Page cache. Recent data is served from memory without Kafka managing its own cache.
  • Batches. One network request and one disk write carry many records. A batch is stored exactly as the producer sent it, including its compression.
  • Zero-copy. For connections without encryption, the operating system sends file bytes straight to the network socket. The bytes do not pass through the Kafka process.

A read: how the broker finds an offset

A consumer asks for "partition 0, from offset 1740". The broker must find the byte position of that record without reading the whole log. It does this in three steps. Run the demo to see each one.

Try it: find a record by offset

  1. Pick the segment. Choose the segment with the largest base offset that is not greater than the target.
  2. Search the index. The .index file is sparse: it has an entry for only some offsets. Binary search finds the nearest entry at or before the target.
  3. Scan the log file. Start at that byte position and read forward until the target offset.

Retention: deleting old data

With cleanup.policy=delete, the default, a background task checks each partition every 5 minutes (log.retention.check.interval.ms). It removes segments that break a rule:

  • Time: the newest record in the segment is older than retention.ms (default 7 days).
  • Size: the partition is larger than retention.bytes (default −1, which means no limit). The oldest segments go first.

The important detail: Kafka deletes whole segments, never part of one. A record stays until every record in its segment has expired. So data usually lives longer than retention.ms. Move the slider to see how much longer.

Try it: retention works on whole segments

Retention is 3 days. Records arrive at a steady rate. Change how often segments roll and watch the age of the oldest record that is still on disk.

segments
active segment closed, still on disk deleted

When a segment is deleted, the broker first renames its files with a .deleted ending and removes them one minute later (file.delete.delay.ms). The log start offset moves forward at once.

The active segment is not exempt. If every record in it has expired, the broker starts a new segment and deletes the old one. Step 7 of the lab shows this on the real cluster. An active segment survives only because new records keep arriving in it.

Compaction: keeping the latest value for each key

Some topics hold state, not events. An example is "the current address of each user". For these, age is the wrong rule. You want to keep the newest record for each key for ever and drop the older ones. This is cleanup.policy=compact.

A background thread, the log cleaner, does the work:

  1. It looks only at closed segments. It never touches the active segment.
  2. It reads the part not yet cleaned and builds a map: key → newest offset.
  3. It copies the segments into new files and leaves out every record that has a newer record with the same key.
  4. It swaps the new files in. The offsets of the remaining records do not change, so the log now has gaps.

A record with a key and a null value is a tombstone. It means "delete this key". The cleaner keeps a tombstone for delete.retention.ms (default 1 day) so that consumers have time to see it, and then removes it too.

Failure scenarios

Data stays long after the retention time

What breaks
A topic that gets a few records each hour has retention.ms of 1 day, but still holds records that are a week old.
You observe
One large segment file. The log start offset does not move.
Cause
The segment rolls only every 7 days or 1 GiB, and retention acts on whole closed segments.
Fix
Set segment.ms to a value near the retention time, for example 1 hour to 1 day.

The broker disk fills

What breaks
The broker stops when a data directory has no free space.
You observe
Disk use grows steadily; errors about failed log directories in the broker log.
Cause
Retention is by time only, and traffic grew. retention.bytes is unlimited by default.
Fix
Set retention.bytes as a safety limit and alert on disk use. Size the disk for peak traffic multiplied by retention time and by the number of copies.

A consumer falls behind retention

What breaks
A consumer was offline for longer than the retention time. Its saved offset now points to deleted data.
You observe
An "offset out of range" error. The consumer then jumps according to auto.offset.reset: to the newest data (records are skipped silently) or to the oldest (many records are processed again).
Fix
Alert when lag, measured in time, comes near the retention time. Choose auto.offset.reset on purpose for each consumer.

A compacted topic never shrinks

What breaks
Old values for a key stay for ever; a new consumer reads millions of outdated records.
You observe
The topic grows. A read from the start shows many records for one key.
Cause
The data sits in the active segment, which the cleaner skips. Or the dirty ratio is not reached. Or the cleaner thread stopped after an error.
Fix
Lower segment.ms. Set max.compaction.lag.ms. Look in the broker's log-cleaner.log file for errors.

A record is too large

What breaks
The producer gets a "record too large" error and the record is not written.
Cause
The batch is larger than max.message.bytes, about 1 MiB.
Fix
Prefer to store the large object elsewhere and send a reference. If you must raise the limit, raise it on the topic, the producer, and the consumers together.

Order is lost after adding partitions

What breaks
Events for one customer arrive out of order.
Cause
The partition is the hash of the key divided by the partition count, taking the remainder. A new count sends the same key to a different partition. Old records stay where they were.
Fix
Choose the partition count with room to grow. If you must change it, create a new topic and migrate. You cannot reduce the partition count at all.

A wrong clock blocks retention

What breaks
A producer with a clock set in the future writes a record. Its segment does not look old until that future time has passed, so retention keeps it.
You observe
One old segment stays while newer segments are deleted.
Limit
Kafka 4.3 rejects a record whose time is more than 1 hour ahead of the broker (message.timestamp.after.max.ms, default 3600000). The problem returns if someone raises that limit.
Fix
Keep the default limit, or use LogAppendTime so that the broker sets the time.

Common mistakes and misconceptions

People thinkWhat is true
A record is removed when a consumer reads it.Reading changes nothing in the log. Only retention or compaction removes data.
A topic keeps records in order.Only one partition does. A topic with several partitions has no total order.
Retention of 7 days means data is deleted at 7 days.It is deleted some time after 7 days, when its whole segment has expired and the next check runs.
A compacted topic holds one record for each key.It holds at least the latest record for each key. The active segment and the part not yet cleaned still hold older ones.
Offsets in a partition have no gaps.Compaction leaves gaps, and so do transactions (module 06). Never compute a record count from two offsets and trust it exactly.
More partitions are always better.Each partition costs files, memory, and recovery time. And you cannot reduce the count later.
A record without a key is fine on a compacted topic.Compaction needs a key. The broker rejects records without one on a compacted topic.
Kafka writes every record to disk before it answers.By default it writes to memory and lets the operating system write to disk. Copies on other brokers give the safety.
offset 7

Staff-level questions

Try to answer each one aloud before you open it.

How much disk does a topic need?

Start with: write rate × retention time × number of copies. For 5 MB each second, 7 days, and 3 copies: 5 MB × 604,800 seconds × 3 ≈ 9 TB.

Then add what the simple formula misses. Add one segment for each partition, because retention overshoots by up to a segment. Add index files, a small percentage. Add free space, often 30 to 40 percent, so that a broker can take over partitions from a failed one. Use the compressed size if producers compress.

How do you choose the partition count?

Find the number you need for throughput: target rate divided by what one partition handles on the slowest side, which is usually the consumer. Then find the number you need for parallel consumers, because one partition is read by at most one consumer in a group. Take the larger number and add room for growth, because changing the count later breaks key ordering.

Then check the cost: more files, more memory for indexes, slower recovery after a broker failure, and more small batches at the producer. A count in the tens is normal. A count in the thousands for one topic needs a reason.

A team wants "keep data for ever". What do you tell them?

Ask what they will do with it. If they need the current state for each key, use compaction: size is bounded by the number of keys. If they need the full history, use retention.ms=-1 with tiered storage so that old segments move to cheap storage (module 09).

Point out the costs: a new replica must copy everything, and a consumer that reads from the start takes a long time. Often a database or a data lake is the right home for history, with Kafka as the transport.

A privacy rule says a user's data must be gone in 30 days. Can a Kafka topic meet it?

On a delete topic, set retention plus one segment period below 30 days, for example retention.ms of 25 days and segment.ms of 1 day.

On a compacted topic, write a tombstone for the user's key and set max.compaction.lag.ms so that the cleaner must act in time. The tombstone itself goes after delete.retention.ms. Remember the copies outside the topic: consumer databases, backups, and remote storage.

Another design avoids the problem: encrypt each user's data with a key for that user, and delete the key.

Why does Kafka trust the page cache, and when is that a risk?

Forcing each write to disk would remove most of the speed. Kafka accepts that one broker can lose its newest data in a power failure, and protects the data by copying it to other brokers before it confirms the write.

The risk is a failure that hits all copies at once, such as one power source for all brokers. The answer is to spread brokers across racks or zones, not to force writes to disk.

What do small segments cost?

Each segment is three open files and two memory-mapped indexes. Ten thousand partitions with one-hour segments and seven days of data is more than five million files. The broker can reach the operating system's limit for open files, and start-up and recovery become slow.

So small segments are right for a few low-volume or compacted topics, and wrong as a default for the whole cluster.

When is a log the wrong tool?

When you need to find a record by something other than its offset, a database is better. When each message must be handled once by any free worker, with separate retries for each message, a queue fits better; Kafka's share groups (module 10) cover part of this. When messages are very large, store the object elsewhere. When the volume is small and you already have a database, a table may be enough.

Self-test

Ten questions. Answer first, then open.

1. What does an offset identify?

The position of one record in one partition. It is not unique across partitions or topics.

2. Two records have the same key. What does Kafka guarantee?

They go to the same partition, so consumers see them in the order they were written. This holds while the partition count stays the same.

3. What does the name 00000000000000001000.log tell you?

The first record in this segment has offset 1000.

4. Name three things that make the active segment roll.

It reaches segment.bytes. It reaches the age segment.ms. Its index file is full.

5. How does the broker find offset 1740 quickly?

It picks the segment by base offset, binary-searches the sparse .index for the nearest earlier entry, and scans forward in the .log file from that byte position.

6. retention.ms is 1 day and segment.ms is 7 days on a quiet topic. About how old can a record get?

About 8 days. The segment closes at 7 days. Its newest record must then be 1 day old before the segment can go.

7. What is a tombstone and how long does it live?

A record with a key and a null value. It tells compaction to delete the key. It stays for delete.retention.ms after cleaning, 1 day by default.

8. Why can a compacted topic still hold two values for one key?

The cleaner skips the active segment and runs only when enough of the log is not yet cleaned. Until it runs, older values remain.

9. What is lag?

The log end offset minus the consumer group's committed offset: the records not yet processed.

10. You raise a topic from 3 to 6 partitions. What breaks?

Keys map to different partitions from now on. New records for a key can land in a different partition from its old records, so order for that key is no longer guaranteed across the change.

Monitoring lab

Module 09 listed the signals to watch but could not read them. This lab opens the brokers' metrics, reads each signal by its real name, runs Prometheus with alert rules, and stops a broker to watch the alerts fire and clear.

offset 0

What it is and why it exists

Kafka hides trouble well. A cluster with one broker down still serves every request. A follower that is falling behind causes no error. A disk that fills in six hours looks fine now. Without measurements you learn about each of these when the second fault arrives and something stops.

Monitoring means three things: metrics that the brokers publish, a system that collects them over time, and alerts that tell a person when a number means trouble. The skill is not in collecting everything. It is in choosing a few signals, knowing what each one means, and deciding which ones are worth waking someone for.

The one-sentence version. Read a short list of broker and controller metrics, collect them over time, and alert on lost availability at once and on lost redundancy during working hours.

offset 1

Mental model

Sort every signal into one of three levels. The level decides the response.

LevelMeaningExamplesResponse
Availability lostSome clients are failing now.Offline partitions. Partitions below the in-sync minimum. No active controller.Page a person.
Redundancy lostEverything works, with less protection.Under-replicated partitions. A broker down. A fenced broker.A ticket; fix in hours.
Capacity shrinkingSomething will run out.Disk filling. Request threads busy. Lag growing.A ticket; fix in days.

Use the tiles at the top of the page. In each situation, find the first tile that turned red and decide its level.

Two sources of numbers

  • Inside the broker. Each broker publishes hundreds of metrics through the Java management interface, JMX. These describe what that broker sees and does: its request times, its thread use, the partitions it leads.
  • From outside. An exporter connects like a client and asks the cluster about topics, partitions and offsets. It sees the cluster as applications see it.

The two can give different numbers for what sounds like the same thing. In the lab, with one broker stopped, the exporter counted 57 under-replicated partitions for the cluster, and broker 1's own metric said 31. Both were right: a broker counts only the partitions it leads.

offset 2

How it works internally

Metric names

A broker metric has a domain, a type and a name, written like kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions. Some have more labels, such as the request type. Each has one or more attributes: a simple Value, or for rates and timings a Count, rates over 1, 5 and 15 minutes, and percentiles.

From metrics to alerts

  1. A collector, here Prometheus, reads the numbers every few seconds and stores them with a timestamp.
  2. A rule is an expression over those numbers, for example "the sum of under-replicated partitions is above 0".
  3. A rule has a for time. The condition must hold that long before the alert fires. This filters out a restart that lasts ten seconds.
  4. A firing alert carries a severity label, which decides if it pages a person or opens a ticket.
  5. When the condition stops, the alert clears by itself.

Lag is measured elsewhere

Consumer lag is not a broker metric. It is the difference between a partition's end offset and a group's committed offset, so something must read both. The command-line tool does this (module 03). An exporter can do it too; the one in this lab could not read groups from Kafka 4.3, so the lab has no lag metric.

The alert rules in the lab

- alert: KafkaBrokerDown
  expr: kafka_brokers < 3
  for: 15s
  labels: { severity: page }

- alert: KafkaUnderReplicatedPartitions
  expr: sum(kafka_topic_partition_under_replicated_partition) > 0
  for: 30s
  labels: { severity: ticket }

- alert: KafkaPartitionBelowMinimum
  expr: sum(kafka_topic_partition_in_sync_replica < 2) > 0
  for: 15s
  labels: { severity: page }

In the lab, "broker down" pages, so that you see a page-level alert fire. On a real cluster with three copies and a minimum of 2, one broker down is redundancy lost: a ticket, not a page. Decide severity from what the alert means for clients.

offset 4

Failure scenarios

The monitoring tool cannot read the new Kafka version

You observe
In the lab, the exporter logged "Cannot get consumer group: kafka: broker not connected" every few seconds and published no lag metric. Topic and broker metrics worked.
Cause
The exporter's client library and Kafka 4.3 do not agree on a request. Kafka 4 removed old protocol versions. unverified: I did not find the exact cause
Lesson
Test your monitoring against a new Kafka version before the upgrade, with the same care as an application. A dashboard that goes blank during an upgrade is the worst moment to lose it.

An alert rule that can never fire

What breaks
A rule refers to a metric that does not exist. It evaluates to nothing, shows as "inactive", and looks healthy for ever.
Evidence
My first version of the lab's rules included a lag alert on a metric the exporter never published. Prometheus loaded it without complaint.
Fix
Test every alert by causing the fault, as this lab does. Add an alert for "metric absent".

Counting a per-broker metric as a cluster total

What breaks
A dashboard shows one broker's "under-replicated partitions" and someone reads it as the cluster's number. Or it shows ActiveControllerCount of 0 from one node and someone declares an emergency.
Evidence
Broker 1 reported 31 while the cluster had 57. Broker 1 reported an active controller count of 0 while node 2 was the active controller.
Fix
Add per-broker metrics up over all brokers. For the controller count, alert when the sum is not exactly 1.

Alerts that nobody believes

What breaks
Every rolling restart fires ten alerts. People mute them. The real alert, a week later, is muted too.
Fix
Give each rule a for time longer than a normal restart. Silence alerts during planned maintenance. Remove any alert that has never led to an action.

Watching the average

What breaks
Average produce time is 4 ms and looks fine while one request in a hundred takes two seconds.
Fix
Alert on the 99th percentile. The timing metrics publish percentiles for this reason.

The metrics port is open to everyone

What breaks
The Java management interface can do more than read numbers. An open, unauthenticated port is a way into the broker.
Fix
Keep it on a private network, or require authentication for it. The lab opens it only inside the Docker network.

offset 7

Staff-level questions

You may have five alerts for a Kafka cluster. Which five?

Offline partitions above 0. The sum of active controllers not equal to 1. Partitions below the in-sync minimum above 0. Disk predicted to fill within a day. Consumer lag in time above each critical application's limit.

Those five mean clients are failing or are about to. Everything else, such as under-replicated partitions or thread saturation, is a ticket or a dashboard.

How do you alert on a disk before it is full?

Not on a level alone. Alert on the predicted time to full, from the growth rate over the last hours: a disk at 70% that grows 5% each hour is urgent, and a disk at 85% that has been flat for a month is not. Keep a simple level alert as a backstop.

What is the right way to measure consumer lag?

In time, not in records: how old is the oldest record the group has not processed? Record counts mean different things on a busy and a quiet topic. Compare the time with what the business accepts for that application, and with the topic's retention, because lag beyond retention is data loss.

Also alert when a partition's committed offset has not moved while its end offset has. That catches a stuck consumer before the backlog is large.

Produce latency at the 99th percentile doubled. How do you find the cause from metrics?

The request time metric splits into parts: time waiting in the queue, time on the local disk, time waiting for followers, time to send the answer. Queue time points to saturated request threads. Local time points to this broker's disk. Follower wait points to a slow follower or the network between brokers.

Then compare brokers. One broker different from the rest is a hardware or placement problem. All brokers together is load. unverified: the lab read only the total time

How do you keep monitoring correct through a Kafka upgrade?

Treat the monitoring stack as a client of the cluster with its own compatibility check. Before the upgrade, run the exporters and dashboards against a test cluster on the new version and cause each fault. Add alerts for missing metrics, so that a silent gap is itself an alert. Keep the command-line checks from module 09 in the runbook as a fallback that needs no extra tooling.

What do you show application teams, and what do you keep for the platform team?

Application teams: their own consumer lag in time, their produce error rate and latency, the size and retention of their topics, their quota use. Platform team: broker and controller health, disk, threads, replication.

Teams act on what they can change. A team that sees broker thread metrics can only worry about them.

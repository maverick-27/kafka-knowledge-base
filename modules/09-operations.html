Operations

Running Kafka well is mostly arithmetic and discipline: size the cluster from real numbers, watch a short list of signals, and change one thing at a time. This module gives you the numbers, the signals and the procedures.

offset 0

What it is and why it exists

The earlier modules explained how Kafka works. Operations is the work of keeping it working: enough capacity, safe changes, quick detection of problems, and protection from clients that misbehave.

Kafka is forgiving in one way and strict in another. It keeps serving through a broker failure, a slow disk or a restart, which hides problems until two happen together. And several decisions cannot be undone: a partition count cannot go down, and deleted data does not come back. So operations is about seeing a problem while the cluster still has spare protection, and about thinking before irreversible changes.

This module covers seven areas: sizing, partition counts, the signals to watch, tiered storage, quotas, security, and upgrades.

The one-sentence version. Size from write rate, retention and copies; keep spare capacity for one broker failure; alert on lost redundancy before lost availability; and roll every change through the cluster one broker at a time.

offset 1

Mental model

A broker has four resources. Each has a typical way to run out.

ResourceUsed forHow it runs out
Disk spaceWrite rate × retention × copies.Traffic grows, or retention is raised, and nobody recalculates.
Disk and network throughputClient writes, follower copies, consumer reads.A consumer reads old data from disk, or a broker failure moves load to the others.
MemoryMostly the operating system's page cache, which serves recent data.Readers fall behind what the cache holds, and reads go to disk.
ProcessorRequest handling, encryption, compression work.Many small requests, encryption without hardware support, or the broker re-compressing batches.

The page cache explains a common surprise. A cluster is fast while every consumer reads recent data, because that data is still in memory. One consumer that starts from the beginning of a large topic forces reads from disk, pushes recent data out of memory, and slows everyone.

Size for the day a broker fails

When one broker of N stops, its leaderships move to the others. Each of them carries N ÷ (N − 1) of its normal load. With three brokers that is 50% more. A cluster that runs at 70% on a normal day has no room for this. So the target on a normal day is well below that.

offset 2

How it works internally

Sizing, with the arithmetic shown

  1. Stored data = write rate × retention time × copies ÷ compression ratio. Use the compressed rate if producers compress.
  2. Add the overshoot. Retention deletes whole segments (module 01), so add one segment for each partition, and a few percent for index files.
  3. Add free space. Plan for disks at most about 60% full. The rest absorbs growth, a reassignment, and the extra a broker receives when another one fails.
  4. Network. Each megabyte written by a client is also sent to each follower. Inbound traffic to the cluster's brokers is write rate × copies. Outbound is the follower traffic plus every consumer group's reads.
  5. Memory. Give the broker's Java process a modest fixed amount and leave the rest of the machine's memory to the page cache. A useful target is enough cache to hold the last 30 seconds to few minutes of writes. unverified rule of thumb
  6. Test. Run the performance tools from module 02 with your record sizes on the real hardware. Published numbers from other people's hardware are a starting point only.

Tiered storage

Keeping months of data on broker disks is costly, and a broker with a lot of local data takes long to replace. With tiered storage, a broker copies closed segments to cheaper remote storage, such as an object store, and deletes its local copy after a short local retention. Consumers that read old offsets are served from the remote copy by the broker; clients do not change.

  • The broker switch is remote.log.storage.system.enable, off by default. A storage plug-in for your object store must be installed.
  • A topic opts in with remote.storage.enable=true and sets local.retention.ms for the local part. retention.ms stays the total.
  • Only closed segments are copied. The active segment is always local.
  • Reads of old data are slower, and have a cost in requests to the object store.

The lab cluster has no remote storage plug-in, so I did not run it in this module. Module 14 runs it with a plug-in and shows segments moving to remote storage and being read back.

Quotas

A quota limits what one client can take, so that one application cannot starve the others. You can limit bytes produced each second, bytes fetched each second, and the share of broker request time. A quota is attached to a user, to a client id, or set as a default.

The broker does not reject requests over quota. It measures the rate over a window, 11 samples of 1 second by default, and when a client is over, it delays its responses and tells the client to wait. So a short burst passes, and a steady overload is slowed to the limit. The lab shows the burst effect.

Security in three layers

LayerQuestionMechanism
EncryptionCan someone on the network read the traffic?TLS on the listener.
AuthenticationWho is this client?TLS client certificates, or SASL with a password, a token, or Kerberos.
AuthorizationWhat may this client do?Access control lists, checked by an authorizer on the broker.

Each listener is a port with its own security settings. A common layout has one listener for clients with TLS and authentication, one for traffic between brokers, and one for controllers on a private network.

The lab cluster has none of this. Its listeners are PLAINTEXT and its authorizer.class.name is empty, so anyone who can reach a port can read, write and delete everything. That is acceptable only on your own machine. Module 11 builds and tests a secured cluster.

Changing settings

Topic settings and many broker settings can be changed while the cluster runs, with kafka-configs.sh. The change is stored in the metadata log and applies to every broker without a restart. Other broker settings are read only at start and need a rolling restart. The tool's output shows where each value comes from: a default, the broker's file, or a dynamic change.

offset 4

Failure scenarios

A disk fills

What breaks
The broker marks the data directory as failed and stops serving its partitions, or stops completely.
Cause
Growth without a recalculation; retention raised on a large topic; a compacted topic whose cleaner stopped; a reassignment that copied more than expected.
Fix
In an emergency, lower retention.ms on the largest topics and wait for the retention check, up to 5 minutes. Do not delete files by hand. Afterwards, alert at 60% and 75%, and set retention.bytes as a limit on topics that can grow without bound.

A second broker fails during a restart

What breaks
With three copies and a minimum of 2, one broker down is fine. Two down stops writes for partitions on both.
Cause
The operator restarted the next broker before the first had rejoined every in-sync set, or a broker failed by itself during the maintenance.
Fix
Check for zero under-replicated partitions before each restart. Automate the check so that it cannot be skipped.

One reader of old data slows the cluster

You observe
Produce latency rises on a broker with no change in write rate. Disk reads jump.
Cause
A consumer reads from far back. Its data is not in the page cache, so the broker reads from disk and recent data is pushed out of memory.
Fix
Put a fetch quota on bulk readers. Run large replays outside peak hours. With tiered storage, old reads go to remote storage and do not disturb the local disk.

Adding partitions breaks ordering

What breaks
Events for one key are processed out of order after a partition increase.
Evidence
In the lab, the topic orders went from 3 to 6 partitions. The key user-42 had been in partition 1 and its next record went to partition 4. The keys user-17 and user-1 stayed where they were.
Fix
Choose the count with growth in mind at creation. For a keyed topic that must grow, create a new topic and migrate. The count can never go down: the tool answers "3 would not be an increase".

Too many partitions

What breaks
Broker restarts and failovers take long. The controller is busy. Producers make many tiny batches.
Cause
Hundreds of topics created with a large default count "to be safe".
Fix
Size each topic. Keep the total for each broker inside what you have tested. Small topics are fine with 1 to 3 partitions.

A topic that nobody protected

What breaks
A topic with one copy loses its data when its broker's disk fails.
Evidence
The lab's check for partitions under the in-sync minimum found a topic named no-quorum with one replica, left over from module 05, on a cluster whose minimum is 2. Nothing can be written to it with acks=all.
Fix
Review all topics for replication factor and minimum regularly. Turn off automatic topic creation and create topics through a reviewed process.

An open cluster

What breaks
Any process on the network can delete topics or read every record.
Cause
Plain-text listeners and no authorizer, as in the lab.
Fix
TLS, authentication and access control lists before any real data arrives. Adding security later needs a careful migration with two listeners.

Common mistakes and misconceptions

People thinkWhat is true
Give the broker's Java process most of the memory.Kafka relies on the operating system's page cache. A large Java heap takes memory away from it and makes pauses longer.
Disk at 85% is fine while it works.One broker failure or one reassignment can fill it. Keep about 40% free.
More partitions is the safe default.Each has a cost, and the count cannot be reduced.
Under-replicated partitions will fix themselves.Often, after a restart. A count above zero that stays is a broker in trouble.
A quota rejects requests over the limit.It delays responses, measured over a window. Bursts pass.
We will add security later.Later means a migration with every client. Start with it.
Tiered storage is a backup.It is the same data in a cheaper place. A deleted topic is deleted there too.
A change that worked on one broker is safe to apply to all at once.Roll it, one broker at a time, with a health check between.
offset 7

Staff-level questions

Size a cluster for 100 MB each second, 7 days of retention, 3 copies.

Storage: 100 MB × 604,800 seconds × 3 = about 181 TB without compression. With a 4-times ratio, about 45 TB. With 40% free, provide about 76 TB. With 4 TB for each broker that is 19 brokers by disk alone; with 8 TB, 10 brokers.

Network: clients send 100 MB each second and followers receive 200 more, so about 300 MB each second inbound across the cluster, plus consumer reads outbound. Check each broker's share against its network link, after one broker has failed.

Then say what you would do next: confirm the compression ratio on real data, test one broker's limits on the real hardware, and consider tiered storage, which could cut local disk to a day or two.

One large cluster or several smaller ones?

One cluster is cheaper to run, makes data easy to share, and uses hardware well. But every tenant shares its failures, its upgrades and its limits, and one bad client or topic can hurt all.

Several clusters isolate failure and let teams upgrade at their own pace, at the cost of more operations work and of copying data between clusters. A common result: a few clusters split by criticality or by data sensitivity, not one for each team. Quotas and access control are what make sharing a cluster workable.

When is tiered storage worth it?

When retention is long compared with how far back most consumers read. Then most local disk holds data that is rarely touched. Moving it out cuts disk cost and makes brokers faster to replace and to rebalance, because there is less local data to copy.

It is not worth it for short retention, or when consumers often read old data and need the speed of local disk. Check also how it combines with compacted topics in your version before you plan on it.

How do you add security to a running open cluster with no outage?

Add a second, secured listener beside the open one, with a rolling restart. Move clients to it application by application. Turn on the authorizer in a mode that still allows clients without rules, add access rules for each application, and watch the authorizer's log for requests that would be denied. When nothing would be denied, switch to deny by default. Finally remove the open listener with another rolling restart.

The slow part is finding every client. Use broker request logs and connection metrics by listener.

Which alerts page a person at night, and which wait for the morning?

Night: offline partitions; no active controller; partitions under the in-sync minimum on critical topics; a disk about to fill within hours; consumer lag beyond a business limit on a critical flow.

Morning: under-replicated partitions with one broker down; a rising trend in disk use; frequent in-sync set changes; one consumer group slowly falling behind. These mean reduced protection, not lost service. Paging for them trains people to ignore pages.

A team asks for 500 partitions for a new topic. What do you ask?

Their peak rate and how much one consumer instance processes, which gives the real need. Whether records have keys, since that decides if the count can ever change. How many consumer instances they will actually run. And how many other topics of this size the cluster already has.

Most requests like this come from a guess. A measured answer is often 12 to 48, with room to grow.

offset 8

Self-test

1. Give the basic formula for stored data.

Write rate × retention time × copies, divided by the compression ratio.

2. Why keep about 40% of the disk free?

For growth, for the retention overshoot, for reassignments, and for the extra load when another broker fails.

3. What memory serves recent data to consumers?

The operating system's page cache, not the broker's Java heap.

4. Which three command-line checks show partition health?

kafka-topics.sh --describe with --unavailable-partitions, --under-min-isr-partitions and --under-replicated-partitions.

5. What must be true before you restart the next broker in a rolling restart?

No partition is under-replicated: the last broker has rejoined every in-sync set.

6. What happens to a key's partition when you add partitions?

It can change, because the partition is the key's hash modulo the count. In the lab user-42 moved from 1 to 4.

7. How does a broker enforce a quota?

It measures the client's rate over a window and delays responses when the client is over the limit.

8. What does tiered storage move, and what stays local?

Closed segments are copied to remote storage and removed locally after the local retention. The active segment stays local.

9. Name the three layers of security.

Encryption, authentication and authorization.

10. How do you change a topic setting on a running cluster?

With kafka-configs.sh --alter. No restart is needed.

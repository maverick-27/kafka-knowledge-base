Producers

A producer does much more than send a message. It groups records into batches, chooses when to send, waits for a chosen level of confirmation, and tries again after a failure without creating duplicates.

1 send()Your code hands over a key and a value.
2 SerializeKey and value become bytes.
3 PartitionThe key's hash picks a partition.
4 BatchThe record waits in memory with others for the same partition.
5 SendA background thread sends full or old batches to the leader.
6 ConfirmThe broker answers. Your callback runs.

Steps 1 to 4 run in your thread and return at once. Steps 5 and 6 happen later, in the producer's own sender thread. This is why send() returns before the record is safe.

offset 0

What it is and why it exists

A producer is the client library that writes records to Kafka. It runs inside your application. It finds which broker leads each partition, sends records there, and handles failures.

The producer exists as a smart client because of speed and safety. If each record made its own network request, Kafka would be slow. So the producer collects records into batches. And networks fail, so the producer retries. A retry can write the same record twice, so the producer and the broker count records to detect a repeat. This is idempotence: doing the same thing twice has the same result as doing it once.

Three decisions matter most. How long to wait for a batch to fill. How many brokers must have the record before the producer treats it as written. And what to do when a write fails.

The one-sentence version. The producer trades a few milliseconds of delay for large batches, waits for the level of confirmation you choose, and retries safely because every batch carries a sequence number.

offset 1

Mental model

Think of a post office counter. You hand over a letter and leave at once. Behind the counter is one bag for each destination. A van leaves when a bag is full, or when the bag has waited long enough. The driver brings back a receipt, and only then do you know the letter arrived.

  • The bag is a batch: one for each partition.
  • Full is batch.size, measured in bytes.
  • Waited long enough is linger.ms.
  • The receipt is the acknowledgement, set by acks.

Use the demo to feel the trade. A slow stream of records with no waiting gives one tiny batch for each record. A little waiting gives large batches and far fewer requests.

How it works internally

The path of one record

  1. Metadata. On the first send to a topic, the producer asks any broker which broker leads each partition. It keeps the answer and refreshes it every 5 minutes (metadata.max.age.ms) or after an error.
  2. Serialize. The key serializer and value serializer turn your objects into bytes.
  3. Partition. With a key: murmur2 hash of the key bytes, remainder after division by the partition count. Without a key: the producer picks one partition and stays on it until about batch.size bytes have gone there, then picks another. It prefers brokers that answer quickly.
  4. Accumulate. The record joins the open batch for its partition, in a memory pool of buffer.memory bytes. If the pool is full, send() waits up to max.block.ms and then throws an error.
  5. Send. The sender thread takes every batch that is full or older than linger.ms, groups them by broker, and sends one request to each broker. Up to 5 requests can be waiting for an answer on one connection.
  6. Answer. On success, the producer completes the record's future and calls your callback with the partition and offset. On a failure that can be retried, the batch goes back in the queue.

Compression

The producer compresses a whole batch, not single records. Larger batches compress better. The broker stores the batch as it arrives, and the consumer decompresses it. So the processor cost is paid by the clients, and the saving applies to the network, the disk and the copies on other brokers.

Retries and the delivery timeout

The producer retries almost without limit: retries is 2147483647. The real limit is time. delivery.timeout.ms, 2 minutes by default, counts from the moment send() returns. It covers the wait in the batch, every attempt, and every pause between attempts. When it ends, the producer gives up and reports an error for the record.

Some errors are worth a retry: the leader moved, a request timed out, too few brokers are in sync. Others are not, and fail at once: the record is too large, serialization failed, the client is not allowed to write.

Idempotence: how a retry avoids duplicates

A retry is dangerous. Suppose the broker wrote the batch but its answer was lost. The producer sends the batch again, and the log now holds it twice. A second danger is order: batch 1 fails, batch 2 succeeds, then the retry of batch 1 lands after batch 2.

Idempotence, on by default, fixes both:

  1. At start, the broker gives the producer a producer id.
  2. The producer numbers the records for each partition: sequence 0, 1, 2, and so on. Each batch carries its first sequence number.
  3. The broker remembers the last five batches from each producer id for each partition. unverified
  4. If a batch arrives with a sequence number the broker has already written, the broker answers "success" and writes nothing.
  5. If a batch arrives with a sequence number that leaves a gap, the broker rejects it. The producer then sends the missing batch first.

The limit of idempotence. It protects against duplicates from the producer's own retries, inside one producer session. It does not help if your application calls send() twice for the same event, or if the application restarts and sends again: a new session gets a new producer id. For those cases you need transactions (module 06) or a consumer that can detect repeats.

Idempotence needs acks=all, at most 5 requests in flight, and retries above 0. If you set a value that conflicts with these and also set enable.idempotence=true, the producer refuses to start.

offset 4

Failure scenarios

The result of send() is ignored

What breaks
Records are lost and nobody knows. This is the most common producer bug.
Cause
send() returns a future. An error arrives later, in the future or the callback. Code that reads neither never sees it.
Fix
Always pass a callback that logs and counts errors, or wait for the future.

Too few brokers are in sync

What breaks
Every write with acks=all fails.
You observe
NOT_ENOUGH_REPLICAS in the producer log, repeated until the delivery timeout. The lab shows it.
Cause
Fewer brokers are in sync than min.insync.replicas. The broker refuses the write because it cannot keep the promise.
Fix
Bring the broker back. Do not lower the minimum to 1 as a quick fix: that removes the protection you set it for.

The delivery timeout expires

You observe
An error like "Expiring 12 record(s) for orders-3: 120000 ms has passed since batch creation".
Cause
The leader was unreachable or too slow for 2 minutes. Or the producer creates records faster than the broker accepts them.
Fix
Find why the broker is slow before you raise the timeout. Decide what your application does with a record that failed: retry later, write to a fallback store, or stop.

The producer's memory is full

What breaks
send() stops returning at once. After max.block.ms it throws a timeout error.
Cause
Your code produces faster than the sender thread can send, so buffer.memory fills.
Fix
Treat it as back-pressure: slow the source. Larger batches and compression raise the send rate. More memory only delays the problem.

acks=1 loses a confirmed record

What breaks
The producer received success, but the record is not in the topic.
Cause
The leader answered and then failed before any follower copied the record. The new leader never had it.
Fix
Use acks=all for data you cannot lose.

One partition is much busier than the others

You observe
One partition grows fast and its consumer falls behind, while others are idle.
Cause
Key skew. One key, or a null-like value such as "unknown", carries a large share of the records.
Fix
Choose a key with more distinct values, or add a second part to the key. For one very large customer, use a custom partitioner that spreads that customer over several partitions, if you can accept less ordering for it.

Duplicates after an application restart

What breaks
The same event is in the topic twice, with idempotence on.
Cause
The application crashed after send() but before it recorded that the event was sent. After the restart it sends again with a new producer id.
Fix
Use the outbox pattern (module 08) or transactions (module 06), or make the consumer ignore repeats by an event id.

So acks=1 below the minimum is "accepted but not visible". Module 04 explains the mechanism, the high watermark.

Common mistakes and misconceptions

People thinkWhat is true
send() returned, so the record is written.It is only in the producer's memory. It is written when the future completes without an error.
Idempotence gives exactly-once delivery.It removes duplicates from the producer's own retries in one session. Exactly-once from end to end needs transactions and care at the consumer.
linger.ms adds that delay to every record.It is the longest wait. A full batch leaves at once, and under load batches fill before the time ends.
batch.size is a number of records.It is a number of bytes.
acks=all means all brokers.It means all brokers that are in sync at that moment. That can be one broker, unless min.insync.replicas says otherwise.
Records without a key are spread one by one over partitions.They go in groups: the producer stays on a partition for about one batch.
Lower retries to avoid duplicates.Idempotence removes the duplicates. Fewer retries only lose more records.
One producer for each thread is safer.The producer is safe to share between threads, and one shared producer makes better batches.
offset 7

Staff-level questions

Product wants "no lost orders and no duplicate orders". What do you build?

For loss: acks=all, three copies, min.insync.replicas=2, and code that handles the send error. For duplicates from retries: idempotence, which is on by default.

Then name the gap. The order is first saved in a database and then sent to Kafka. A crash between the two steps loses or repeats the event. Close the gap with the outbox pattern: write the event to a table in the same database transaction, and let a separate process copy the table to Kafka. Consumers still get the event at least once, so give each event an id and make consumers ignore repeats.

How do you tune a producer for latency below 10 milliseconds?

Set linger.ms=0 and keep batches small enough that they do not wait. Keep acks=all if the data matters, and make replication fast instead: brokers close to each other, fast disks. Turn off compression or use lz4. Measure the 99th percentile, not the average, and watch for pauses in the client's runtime.

Then ask if 10 milliseconds is really needed from end to end, because the consumer's fetch settings add delay too.

A broker is slow but not dead. What happens to producers?

Batches for the partitions it leads wait longer. They fill buffer.memory, and then send() blocks for every partition, also the healthy ones. One slow broker can stall the whole producer.

Defences: for records without keys, the adaptive partitioner sends less to the slow broker, and partitioner.availability.timeout.ms can exclude it. For records with keys there is no escape, so keep max.block.ms low enough that your application fails fast, and alert on the producer's buffer and request latency metrics.

Why can max.in.flight be 5 and order still be safe?

The broker keeps the sequence numbers of the last five batches for each producer and partition. If batch 1 fails while batches 2 to 5 are in flight, the broker rejects 2 to 5 because they leave a gap, and the producer resends all of them in order. More than five could not be checked, which is why the limit is 5.

What is a good key?

The thing whose events must stay in order: an order id, an account id, a device id. It should have many distinct values, with no single value that dominates. It should be stable: the same entity always gives the same key.

Check the two failure cases. A key with few values, such as a country, gives hot partitions. A random key gives a perfect spread and no useful order.

Where should compression happen?

In the producer. It then saves network, broker disk, replication traffic and consumer network at once. The topic setting compression.type=producer, the default, tells the broker to keep the batch as it arrived.

If the topic names a different codec, the broker must decompress and compress again, which costs broker processor time. Avoid that.

offset 8

Self-test

1. When is a batch sent?

When it reaches batch.size bytes, or when it has waited linger.ms, whichever comes first.

2. What is the default for linger.ms in Kafka 4?

5 milliseconds. Before 4.0 it was 0.

3. What does acks=all wait for?

All brokers that are in sync for that partition at that moment have copied the record.

4. What happens to a write with acks=all when fewer brokers are in sync than min.insync.replicas?

The leader refuses it with NOT_ENOUGH_REPLICAS. The producer retries until the delivery timeout.

5. Which setting really limits retries?

delivery.timeout.ms, 2 minutes by default.

6. Which three values identify a batch for duplicate detection?

The producer id, the producer epoch, and the sequence number for that partition.

7. Name one duplicate that idempotence does not prevent.

The application sends the same event again after a restart, or calls send() twice. A new session has a new producer id.

8. Where do records without a key go?

To one partition for about one batch, then to another. The producer prefers brokers that answer quickly.

9. send() blocks and then throws a timeout. Name two causes.

The memory pool buffer.memory is full, or the producer cannot get metadata for the topic. Both wait up to max.block.ms.

10. Why do larger batches compress better?

Compression works on the whole batch, and more records give more repeated content to remove.

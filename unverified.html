Unverified claims

Every statement in the modules that I could not confirm against the Kafka 4.3 documentation or the lab cluster. Each one is also marked in red where it appears. Check these before you rely on them.

What "verified" means here. A config default counts as verified when I read it from the Kafka 4.3 reference pages or from the running lab cluster. A behaviour counts as verified when a lab command showed it. Everything else that is specific to a version is in this list.

Also worth knowing

  • Five items that were on this list are now verified by labs: broker metric names (module 12), security (module 11), Debezium behaviour and a stopped connector (module 13), and tiered storage (module 14).
  • The case studies are public write-ups read from the outside. Three candidate cases (a "Kafka 4.0 on Kubernetes" postmortem, a "$2.3M fintech" story, and Uber's multi-region disaster recovery blog) were dropped because they could not be confirmed. The question and recipe items above are advice, not measurements.
  • Lab outputs are from one run on one laptop, on 4 and 5 October 2026, with image apache/kafka:4.3.1. Throughput and timing numbers will differ on your machine.
  • The Java code sample in module 07 was not compiled. The lab ran the original example from the Kafka image.
  • The last step of module 07's lab, the application reset, was not run after the wait it needs.
  • Explanations of long-standing designs, such as the page cache, the in-sync set and Raft voting, are from general knowledge. They are not marked one by one.
